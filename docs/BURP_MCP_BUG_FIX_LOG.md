## Responsiveness finding

The historical audit reproduced a service-wide MCP stall while TCP listeners remained open and captured a JVM dump with 99 threads, without a deadlock marker. It did not prove executor starvation, approval blocking, or a specific lock cause. During this verification the loaded MCP server answered live read-only calls, and the LOCAL suite passed eight MCP integration tests, including eight concurrent status requests during one mocked pending approval. The historical freeze was not reproduced; it is **unresolved**, not fixed.

Source review confirms Ktor/Netty handles MCP requests; KtorServerManager's single-thread executor serializes server lifecycle start/stop work. DecisionQueue waits without holding its synchronized lock and are bounded by the message deadline. These findings do not establish why the historical service-wide freeze occurred.

## Desktop-control limitation

The supported `cua.getState()` and `cua.listWindows()` calls both failed with `Computer Use native pipe is unavailable: failed to connect native pipe: The system cannot find the file specified`; the browser access host was also unavailable. A fresh `cua_repl` reset and reconnect did not restore access. Focused Windows inspection found the `codex-computer-use-swift.exe` helper responding under the same Windows user and interactive session as the current shell; its parent is `ChatGPT.exe`. A matching named-pipe endpoint is visible, but the helper command line contains no pipe identifier and the supported API cannot establish which process owns that endpoint. The installed `@oai/cua`/`@oai/sky` package versions are 0.2.6/0.7.13; helper file version metadata is absent. No relevant recent CUA log files or matching Windows Application error events were found. The installed transport source confirms that the API attempts `createConnection` using `SKY_CUA_NATIVE_PIPE_DIRECTORY` and wraps the OS error; this exact failure occurs at that connection step. These facts rule out a missing helper and basic user/session mismatch, but cannot distinguish an endpoint namespace/identifier mismatch, an unavailable pipe instance, or a host/client compatibility issue. Elevation parity is not exposed through the supported interface. No supported host restart/rebind control or alternate Windows UI tool is available here. No direct named-pipe client, alternate UI automation, helper termination, or security-setting change was attempted. Burp's activation control could not be observed or operated, leaving live unattended testing blocked.

## Supervised coordinator

`scripts/run-supervised-reliability-suite.ps1` now provides OFFLINE, LOCAL, and SUPERVISED modes. SUPERVISED mode reads the active identities from authenticated MCP into process memory, requires the exact nine target scope checks and an empty queue, starts the identity-bound fixture, passes setup preflight before requesting an interception session, then performs one bounded cancellation attempt and verifies drop policy evidence, stale-ID rejection, client outcome, origin non-delivery, and queue cleanup. It uses a 180-second session only when the unattended authorization has enough remaining time; all existing activation, allowlist, expiry, and two-in-flight controls remain in force. It never activates unattended mode, clicks approval dialogs, stores identities/tokens, or retries an ambiguous request.

The offline end-to-end PowerShell simulation passed 22 assertions covering successful orchestration, setup failure gating, fixture cleanup, inactive-authorization blocking, and propagation of BLOCKED/INCONCLUSIVE results. A separate 10-assertion local test exercised the actual fixture launcher with process-environment identities, confirmed matching health headers and no identity/token exposure in command-line/output, and released its listener. The real current-state preflight confirmed authentication and scope calls but correctly stopped before fixture/session startup because unattended mode is inactive. Phase 4A is still INCONCLUSIVE.

The top-level OFFLINE/LOCAL coordinator now reads the full validation JSON counts. Any FAIL remains FAIL; BLOCKED checks remain BLOCKED; INCONCLUSIVE or UNVERIFIED checks remain INCONCLUSIVE; only a run with no such outcomes is PASS. Offline simulations cover each classification. The full OFFLINE run returned 18 PASS, 3 BLOCKED, 2 UNVERIFIED and an aggregate BLOCKED. The latest LOCAL run returned 21 PASS, 2 UNVERIFIED and an aggregate INCONCLUSIVE.
